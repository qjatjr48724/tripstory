# 여행 일정 관리 앱 개발 제안서 / 요구사항 명세서

**앱 이름:** tripstory

> 여행을 계획하고 → 함께 관리하고 → 여행 중 사용하고 → 비용을 정산하고 → 여행이 끝난 뒤 기록으로 남기는 모바일 앱

본 문서는 Cursor 등 AI 개발 도구가 프로젝트의 목적, 기능, 데이터 관계, 권한과 예외 상황을 이해하고 일관된 방향으로 개발할 수 있도록 작성한 기준 문서입니다.

- **확정 항목:** 현재까지 결정된 요구사항
- **확장 아이디어:** 초기 개발 이후 검토할 기능

# 1. 서비스 개요

## 핵심 컨셉

> 여행을 계획하고 → 함께 관리하고 → 여행 중 사용하고 → 비용을 정산하고 → 여행이 끝난 뒤 기록으로 남기는 앱

하나의 여행 데이터 안에서 여행 일정, 장소 후보, 지도, Plan B, 예약 정보, 여행 비용, 정산, 사진, 링크 등을 통합 관리한다. 혼자 여행할 때도 사용할 수 있고 여러 명이 하나의 여행 데이터를 공유할 수 있다.

## 핵심 사용자 흐름

1. 계정 생성 / 로그인
2. 여행 생성 또는 초대코드로 참여
3. 장소 후보와 일정 공동 관리
4. 여행 중 일정 / 예약 정보 조회
5. 여행 비용 입력 및 정산
6. 사진과 여행 데이터 기록
7. 여행 완료 후 기록 보존
8. 여행 보고서 PDF 생성

## 기술 방향

| 항목 | 방향 |
|---|---|
| 클라이언트 | Flutter + Dart |
| 백엔드 | Supabase (Auth / DB / Storage / Realtime 등) |
| 플랫폼 | Android + iOS |
| 국내 지도 | Naver Map |
| 해외 지도 | Google Maps |
| 기본 통화 | KRW |

# 2. 계정 및 여행 생성

## 2.1 계정

- 계정 생성과 로그인이 필요하다.
- 이메일 가입은 실제 사용 중인 이메일의 인증을 완료해야 한다.
- 초기 인증(MVP)은 **이메일 + Google + Apple**을 포함한다.
- Kakao / Naver는 후순위다.
- 여러 인증 방법을 하나의 계정에 연결할 수 있다.
- 최소 하나의 로그인 방법은 항상 유지해야 하며 유일한 인증 방법은 삭제할 수 없다.

## 2.2 여행 데이터

- 여행마다 하나의 독립된 여행 데이터를 만든다.
- 여행 데이터는 계정에 저장되며 여행 종료 후에도 남는다.
- 완료된 여행은 삭제하지 않고 **편집이 종료된 여행 기록**으로 보존한다.
- 여행을 생성한 사용자가 자동으로 여행장이 된다.

## 2.3 여행 생성

| 항목 | 필수 | 설명 |
|---|---|---|
| 여행 이름 | 필수 | 여행 식별 이름 |
| 여행 기간 | 필수 | 시작일 / 종료일 |
| 여행 지역 | 필수 | 넓은 범위의 지역 |
| 여행장 | 자동 | 여행 생성자 |
| 간단 메모 | 선택 | 기본 메모 |

## 3.1 초대코드

- 6자리
- 영문 대문자 / 소문자 / 숫자 조합
- 대소문자 구분
- 여행 중에도 구성원 참여 가능

## 3.3 여행장 이전 및 구성원 이탈

- 여행장 이전은 현재 여행장과 새 여행장 후보자 모두 동의해야 한다.
- 여행장은 소유권 이전 없이 여행에서 나갈 수 없다.
- 일반 구성원은 자발적으로 나갈 수 있다.
- 강제 퇴장된 구성원은 다시 초대할 수 있다.
- 구성원이 나가도 자신이 등록한 장소 및 관련 여행 데이터는 유지한다.
- 재참여하면 기존 작성자 연결을 복구한다.
- 구성원별 장소 색상을 사용한다.
- 구성원이 이탈하면 해당 구성원의 장소는 비활성 색상으로 표시할 수 있다.
- 재참여하면 원래 구성원 색상을 복구한다.
- 별도로 "탈퇴한 구성원"이라는 문구를 장소에 표시할 필요는 없다.

# 4. 장소 후보 및 지도

## 4.1 장소 후보

장소 후보는 일정과 독립된 핵심 개념이다. 일정에 넣지 않고도 가고 싶은 장소를 먼저 저장할 수 있어야 한다.

### 등록 흐름

1. 장소 후보 등록
2. 한 번만 다음 질문 표시

> 해당 장소를 일정에 추가할까요?

3. **예**
   - 장소 정보가 미리 입력된 일정 등록 화면으로 이동
   - 사용자가 시작 시간 / 메모 등을 입력
4. **아니오**
   - 장소 후보로만 저장

### 장소와 일정 관계

- 일정을 삭제해도 장소 후보는 남는다.
- 일정에서 장소를 제거해도 장소 후보는 남는다.
- 장소 자체를 삭제하려면 일정에 연결된 경우 먼저 일정에서 연결을 해제해야 한다.
- 장소에는 등록 구성원의 `member ID`를 저장한다.

## 4.2 지도

| 장소 | 지도 |
|---|---|
| 대한민국 주소 | Naver Map |
| 대한민국 외 | Google Maps |
| 복수 국가 여행 | 장소 국가에 따라 국내 Naver / 해외 Google |

## 4.3 경로 시각화

이 앱의 경로는 **실제 길찾기 기능이 아니다.** 이동수단, 도로, 이동시간은 계산하지 않고 **일정 순서만 시각화**한다.

- 일정에 연결된 장소의 좌표를 일정 순서대로 가져온다.
- `A → B → C → D`의 좌표를 순서대로 선으로 연결한다.
- 실제 도로를 따라가는 라우팅 API는 필수가 아니다.
- 일정 순서를 변경하면 선의 연결 순서도 변경한다.

# 5. 일정 및 Plan B

## 5.1 일정 구조

```text
여행
 ├─ 날짜 1
 │   ├─ 일정 1
 │   └─ 일정 2
 └─ 날짜 2
     ├─ 일정 1
     └─ 일정 2
```

- 일정은 날짜 아래에 존재한다.
- 시작 시간만 저장하며 종료 시간은 저장하지 않는다.
- 드래그 앤 드롭으로 순서를 변경한다.
- 순서를 변경해도 시간이 자동으로 바뀌지 않는다.
- 시간과 순서는 별도 값이다.
- 방문 완료 체크 / 상태를 제공한다.
- 모든 구성원이 일정을 수정할 수 있다.
- 장소 후보와 일정은 독립적이다.
- 장소를 일정에 연결할 수 있다.

## 5.2 Plan B

- 각 주요 목적지에 최대 2개의 Plan B를 등록한다.
- 예: 메인 A / Plan B 1 = B / Plan B 2 = C
- 초기 버전에서는 단순 대체 장소 연결로 구현한다.

# 6. 비용 및 정산

## 6.1 비용 필드

| 필드 | 내용 |
|---|---|
| 비용 항목 | 식비, 교통, 숙박, 관광/입장, 쇼핑, 여행 준비, 기타 등 |
| 설명 | 지출 상세 |
| 금액 | 정수 단위 |
| 실제 결제자 | 선결제한 구성원 |
| 결제 수단 | 현금 / 카드 / 모바일 결제 등 |
| 결제 일시 | 비용 발생 시점 |
| 정산 참여자 | 정산할 구성원 선택 |
| 통화 | KRW / JPY / CNY / USD / EUR |
| 정산 제외 | 정산 대상에서 제외 가능 |
| 분담 | 1/N 또는 직접 금액 |
| 정산 상태 | 진행 / 완료 |

## 6.2 정산 규칙

- 1/N 균등 분담을 지원한다.
- 구성원별 직접 금액 입력을 지원한다.
- 실제 결제자와 정산 참여자는 별도 데이터다.
- 정산 참여자는 일부 구성원만 선택할 수 있다.
- 여행장이 최종 정산 금액을 결정할 수 있다.
- 송금자는 `보냈어요!` 등의 방식으로 송금 완료를 표시한다.
- 돈을 받는 사람은 실제 입금 확인 후 수령을 확인한다.
- 필요한 송금 / 수령 확인이 모두 완료되면 정산 완료 상태가 된다.
- 정산 완료 후 해당 금액은 수정할 수 없다.
- 비용 삭제는 여행장과 총무만 할 수 있다.
- 정산 참여자 변경은 여행장과 총무만 할 수 있다.
- 금액은 정수 단위이며 소수점을 사용하지 않는다.

## 6.3 나눠지지 않는 금액

균등 분할이 정확히 나누어지지 않는 경우 특정 구성원에게 임의로 1원을 더하지 않는다.
나머지 금액은 **미배분 잔액**으로 표시하고, 사용자가 수동으로 배분한다.

```text
10,000원 ÷ 3명
→ 1인 3,333원
→ 미배분 잔액 1원 (수동 배분)
```

## 6.4 총무

총무는 **여행의 돈에 관련된 역할**이다. 여행장이 총무를 지정한다.

총무는 비용을 먼저 계산 / 지불하고 나중에 구성원에게 정산받을 수 있다.

예:

```text
총무 A
숙박비 300,000원 선결제

B → A 100,000원
C → A 100,000원
A → 나머지 100,000원 부담
```

### 총무 권한 (확정)

- 비용 등록 / 수정
- 비용 삭제
- 정산 참여자 변경
- 최종 정산 금액 확정
- 송금 / 수령 확인 대행 (다른 구성원 건 포함)

### 여행장 전용 (총무에게 부여하지 않음)

- 구성원 초대 / 강제 퇴장
- 여행 삭제 / 여행 완료
- 초대코드 재발급
- 총무 지정 / 여행장 이전

# 7. 통화 및 환율

## 7.1 지원 통화

| 통화 | 기준 |
|---|---|
| KRW | 1원 |
| JPY | 100엔 |
| USD | 1달러 |
| EUR | 1유로 |
| CNY | 1위안 |

- 기본 통화는 KRW다.
- 하나의 여행에서 여러 통화를 사용할 수 있다.
- 환율은 **하루 1회 갱신**한다.
- 환율 표시값은 소수점 둘째 자리까지 표시한다.
- 거래에 실제 적용된 환율은 거래 데이터에 스냅샷으로 저장한다.
- 이후 환율이 갱신되어도 과거 거래에 적용된 환율은 변경되지 않는다.

예: `100 JPY = 950.25 KRW`

## 7.2 환율 적용

- **기본값:** 결제(선결제) 시점의 환율을 사용한다.
- **비용마다 변경 가능:** 정산 시점 환율, 또는 사용자가 직접 입력한 환율.
- 선택한 환율은 해당 거래 데이터에 스냅샷으로 저장하며, 이후 환율이 갱신되어도 변경되지 않는다.
- 외화 예약금을 실제 결제한 경우 사용자가 실제 적용받은 환율을 직접 입력해 저장할 수 있다.

## 7.3 환율 데이터

초기 환율 API 후보는 **한국수출입은행 환율 공공데이터 API**다.

실제 구현 시 제공 시각, 통화별 단위, 갱신 주기, 장애 대응, 사용 정책 및 트래픽 제한을 다시 확인한다.

# 8. 예약 및 예매 정보

예약 기능은 예약을 다시 구매하는 기능이 아니라, 외부 서비스에서 예약한 정보를 여행 중 한곳에서 확인하기 위한 기능이다.

## 예약 유형

- 교통수단: 항공권, 렌트, 기차 등
- 숙소
- 기타 예약 / 예매

## 공통 정보

- 예약자
- 예약번호
- 비용
- 시작 일시 (선택: 탑승 / 체크인 / 이용 시작 시각 등, 있으면 알림에 사용)
- 예약 확인 이미지 / 스크린샷
- 예약 확인 페이지 링크
- 메모

## 숙소 정보

- 숙소 주소
- 객실 정보
- 예약번호 등 식별 정보
- 예약자
- 비용

외부 예약 서비스에서 입력한 모든 정보를 앱에 다시 입력시키지 않는다. 실제 예약 확인에 필요한 최소 정보와 이미지 / 링크를 중심으로 한다.

# 9. 사진

## 9.1 예약 첨부 사진

- 교통 / 숙소 / 기타 예약에 확인 이미지나 사진을 첨부할 수 있다.
- 예약 사진은 해당 예약 데이터와 연결한다.

## 9.2 별도 여행 사진

예약과 별개로 여행 사진을 등록할 수 있는 독립된 공간을 제공한다.

```text
사진 등록
 ├─ 사진
 ├─ 제목
 └─ 메모
```

목록은 썸네일 + 제목 + 짧은 메모 중심으로 표시한다.

여행 완료 후에도 기존 사진은 조회할 수 있다.

| 정산 요청 | 즉시 |
| 정산 완료 | 완료 시 |
| 여행 초대 | 초대 시 |
| 여행장 이전 요청 | 요청 시 |
| 여행 완료 예정 | 3일 전 / 1일 전 / 6시간 전 |

### 알림 수신 설정 (확정)

- 알림 on/off는 **계정 전역**에서 카테고리별로 설정한다.
- 사용자가 해당 알림을 켜 둔 경우에만 발송한다.
- 예약 시작 알림은 시작 일시가 입력된 예약에만 적용한다.
- 구현 시 OS 알림 권한도 함께 설계한다.

# 11. 여행 완료 및 휴지통

## 11.1 여행 완료

> **여행 완료 = 편집 종료 + 기록 보존**

### 완료 방식

1. 여행장의 수동 완료
2. 여행 종료일 7일 후 자동 완료

수동 완료 확인:

> 여행을 완료하시겠습니까?

안내:

> 지금 완료하지 않아도 여행 종료일로부터 7일 후 자동으로 여행 완료 상태로 전환됩니다.

### 완료 후

- 다시 진행 중으로 되돌릴 수 없다.
- 여행 데이터를 수정할 수 없다.
- 구성원은 완료된 여행을 조회할 수 있다.
- 기존 사진을 조회할 수 있다.
- 기존 예약 이미지를 조회할 수 있다.
- PDF 여행 보고서를 생성할 수 있다.
- 기존 백업 스냅샷은 삭제한다.
- 초대코드는 만료된다.

여행 완료는 데이터 삭제가 아니라 **편집 종료와 기록 보존**이다.

## 11.2 휴지통

- 휴지통은 **여행 전체** 삭제에만 사용한다.
- 여행을 삭제하면 그 안의 일정 / 장소 / 비용 / 예약 / 사진 등은 **여행 단위로 묶여** 함께 보관·복원된다.
- 휴지통 보관 기간은 **7일**이다.
- 7일 동안 복원할 수 있다.
- 7일이 지나면 영구 삭제한다.
- 복원 권한은 **여행장만** 가진다. (여행 삭제도 여행장만 가능)
- 일정 / 장소 / 비용 / 예약 / 사진 등 **세부 항목**은 삭제 전 1회 확인 후 **즉시 삭제**하며, 휴지통·복원 대상이 아니다.

# 12. 백업 / 복원

- 여행장이 수동으로 백업을 생성한다.
- 최대 3개의 백업을 보관한다.
- 백업 이름은 `여행 이름 + 날짜 + 시간`으로 자동 생성한다.
- 백업은 동일 여행 안에서만 복원할 수 있다.
- 다른 여행으로 가져올 수 없다.
- 복원은 여행 데이터 전체를 스냅샷 시점으로 되돌린다.
- 복원 전에 현재 상태를 자동으로 백업한다.
- 복원 확인은 강하게 안내한다.

> 복원하면 되돌릴 수 없어요!

### 백업이 3개인 경우

새 백업을 만들면:

1. 가장 오래된 백업이 삭제될 예정임을 알린다.
2. 사용자에게 명시적 동의를 받는다.
3. 가장 오래된 백업 삭제
4. 새 백업 생성

### 복원 전 자동 백업 시 백업이 3개인 경우 (확정)

1. 가장 오래된 백업이 삭제될 예정임을 알린다.
2. 사용자에게 명시적 동의를 받는다.
3. 가장 오래된 백업 삭제
4. 현재 상태 자동 백업 생성
5. 선택한 백업으로 복원

여행 완료 시 백업 스냅샷은 모두 삭제한다.

# 13. 오프라인 및 동시 수정

## 13.1 오프라인

여행에 필요한 데이터를 기기에 미리 저장하여 인터넷 없이 조회할 수 있게 한다.

```text
온라인: 조회 + 수정
오프라인: 조회만 가능
```

오프라인에서 조회 가능한 예:

- 일정
- 장소
- 예약 정보
- 여행 기본 정보
- 기타 여행 중 필요한 데이터

초기 버전에서는 오프라인 수정 및 추후 자동 동기화를 지원하지 않는다.

PDF는 추가적인 오프라인 참고 수단으로 활용한다.

## 13.2 동시 수정 충돌

권장 방식:

> **낙관적 동시성 제어(Optimistic Concurrency Control) + version 필드**

### 예시

1. A와 B가 같은 장소를 편집한다.
2. 현재 version = 3
3. A가 먼저 저장한다.
4. 서버의 version = 4
5. B가 기존 version = 3 상태로 저장한다.
6. 서버가 저장을 거부한다.
7. B에게 다음과 같이 안내한다.

> 다른 구성원이 이 내용을 수정했습니다. 최신 내용을 확인한 후 다시 수정해주세요.

8. 최신 데이터를 다시 불러온다.
9. B가 필요한 내용을 다시 수정하여 저장한다.

### 원칙

- 오래된 데이터가 최신 데이터를 덮어쓰지 않도록 한다.
- 마지막 저장자가 무조건 승리하는 방식은 사용하지 않는다.
- 완벽한 실시간 공동 편집 / 자동 병합 기능은 초기 버전에서 구현하지 않는다.

# 15. 프로필 및 계정 탈퇴

## 15.1 프로필

프로필은 같은 여행의 구성원에게만 노출한다. 공개 커뮤니티 기능은 제공하지 않는다.

| 필드 | 필수 |
|---|---|
| 이름 또는 닉네임 | 필수 |
| 프로필 이미지 | 선택 |
| 연락처 | 선택 |
| 자기소개 | 선택 |
| 배지 / 스티커 / 스킨 | 향후 확장 |

## 15.2 여행별 공개 설정

- 특정 여행의 개인정보 공개 범위는 사용자가 해당 여행에 가입한 시점의 설정을 기준으로 고정한다.
- 이후 프로필 공개 설정을 변경해도 과거 여행에 소급 적용하지 않는다.
- 연락처 등은 같은 여행 구성원에게만 보인다.

## 15.3 계정 탈퇴

- 탈퇴 후 30일 동안 복구 가능
- 30일 후 완전 삭제
- 일반 구성원이 탈퇴해도 장소 / 메모 / 일정 관련 정보 / 사진 / 비용 등 여행 기록은 유지
- 완전 삭제 후 작성자는 `탈퇴한 구성원`으로 표시
- 30일 내 계정을 복구하면 기존 완료 여행 기록도 다시 볼 수 있어야 한다.

### 여행장의 탈퇴

진행 중인 여행이 있는 여행장은 바로 탈퇴할 수 없다.

다음 중 하나를 먼저 해야 한다.

1. 다른 구성원에게 여행장 이전
2. 진행 중 여행 데이터 삭제

완료된 여행만 남아 있다면 여행장 탈퇴가 가능하다.

# 19. 확장 아이디어

초기 개발 범위에는 넣지 않거나 우선순위를 낮추고, 핵심 기능이 안정화된 이후 검토한다.

1. **장소 ↔ 일정 ↔ 지출 연결**
   - 일정의 장소에서 관련 비용을 바로 확인
   - 향후 비용 자동 생성

2. **예약 정보 ↔ 일정 연결**
   - 일정에서 예약 정보 바로 확인
   - 예약 비용과 장부 연계

3. **외부 서비스 연동**
   - 앱 설치 시 앱으로 이동
   - 미설치 시 웹으로 이동

4. **간단 일정 전용 PDF / 축약형 PDF**

5. **스마트 일정 알림**
   - 이동시간
   - 현재 위치
   - 출발 시점

6. **여행 비용 통계**
   - 일별
   - 카테고리별
   - 구성원별 부담
   - 결제수단별

7. **프로필 꾸미기**
   - 배지

# 20. 최종 개발 원칙

1. **여행 데이터 중심**
   - 모든 기능은 특정 여행에 귀속된다.

2. **공동 관리**
   - 여러 구성원이 하나의 여행 데이터를 공유한다.

3. **권한 분리**
   - 여행장 / 일반 구성원 / 총무의 역할을 명확히 한다.

4. **기록 보존**
   - 여행 완료는 삭제가 아니라 편집 종료와 기록 보존이다.

5. **안전한 수정**
   - 동시 수정 시 version 검증으로 오래된 데이터의 덮어쓰기를 방지한다.

6. **오프라인 조회**
   - 여행 중 필요한 데이터는 인터넷 없이도 볼 수 있어야 한다.

7. **재입력 최소화**
   - 예약 정보 등 외부 서비스 데이터를 불필요하게 중복 입력시키지 않는다.

8. **단순 경로**
   - 실제 길찾기가 아니라 일정 순서를 지도에 연결해 보여준다.

9. **과거 거래 보존**
   - 환율과 정산 결과는 당시 적용값을 보존한다.

10. **확장 가능성**
    - 핵심 기능을 우선하되 향후 여행 복사 / 통계 / 검색 등을 추가할 수 있는 구조로 만든다.
